# Soundspan CDN egress: IPv4 for YouTube audio

## Failure and controlled comparison

The Soundspan-only Privoxy bridge sends HTTPS CONNECT through its existing SSH
SOCKS listener. The CDN `rr3---sn-4g5ednkl.googlevideo.com` timed out by hostname
and by its observed IPv6 address, while the same node's IPv4 address connected
in 60 ms. A control CDN connected over both families. This is evidence of a
selective egress-path failure, not a measured YouTube concurrency limit.

An isolated Privoxy listener compared the old and proposed configuration in
old/new/new/old order. The old route timed out twice at 3006 ms. The proposed
route returned the expected root HTTP 404 at 1369/259 ms; the working CDN and
YouTube metadata origin remained reachable. A 262144-byte audio range from the
previously failing track on the same CDN decoded successfully.

## Deployed rule

After the default `forward-socks5t` line in the Soundspan-specific configuration:

```text
forward-socks4 .googlevideo.com:443 127.0.0.1:11080 .
```

SOCKS4 resolves the destination locally to IPv4. The connection still uses the
same authorized SSH tunnel and external source IP. This does not bypass the
proxy, replace the audio version, disable TLS verification, or extend the
existing client access list. Other origins keep their previous SOCKS5 route.
CDN DNS queries therefore use the container host resolver instead of the remote
SOCKS resolver; this scoped behavior is intentional. No fixed CDN IP is stored.

See the official [Privoxy forwarding documentation](https://www.privoxy.org/user-manual/config.html#FORWARD-SOCKS)
for hostname-resolution semantics and last-matching-rule precedence.

## Release and rollback

- Only `/etc/privoxy/soundspan.config` in LXC 121 changed. Configuration validation
  passed before atomic replacement; Privoxy detected the change without restart.
- Privoxy PID 3097 and all running container identities remained unchanged.
  YouTube sidecar image stayed `sha256:b613d2d920b68b04c73277e7cb41c75b97c0d2b97e0faf16307c1ba339f422b5`.
- Configuration SHA256: `bbdec70eded4f24b7b4fedb4093579d1c223e2e9b0fc9f418a09842f1b87395f`.
- Backup: `/srv/music/soundspan-releases/b0-b340a7c/privoxy-before-cdn-ipv4.config`,
  SHA256 `bfee4fbf62a002b865d4f1b7bc285166ba79d3c8bc53cc0bc46600c5254a061e`.
- Rollback restores the validated backup atomically with a fresh modification
  time, then verifies new CONNECT requests. Existing listeners do not require
  restarting; neighboring Soulseek/network services are outside this release.

Post-release, the formerly failing node responded in 223 ms and the control node
in 282 ms. The public application health check returned 200 with healthy database
and Redis dependencies.

## Acceptance boundary

The exact previous 20-track set was downloaded and fully decoded through the
running sidecar, followed by three repeat requests. No backend history or taste
events were written. This is a mixed-cache check, not an all-cold benchmark,
browser audibility measurement, phone-background check, or 100-listener test.

The failed track `5ooz4Ams8-w` previously returned HTTP 502 after 12299 ms; after
the route change, response headers arrived in 1264 ms and its complete 3985113
bytes arrived in 4214 ms with successful full decoding. This case's source-link
cache was not cleared, so its result does not prove a 1.3-second fully cold start.

The IPv6 path itself has not been repaired on the remote host. The released
configuration removes that failing path from Soundspan audio connections.
Cold extraction latency and full playback/load acceptance remain open P0/P7 work.
