# Причина повторных отказов YouTube CDN

verify: исправление выпущено на CT121 12 сентября 2026 года в 23:52:36 UTC
(13 сентября, 02:52:36 MSK). Изменён один runtime-модуль:
`services/ytmusic-streamer/ytmusic_player_cache.py`. Git push не выполнялся.

## Воспроизведение и исправление

verify: в одном процессе последовательность MWEB/PO-запросов трёх настоящих
записей прошла полностью со штатным yt-dlp. Повтор той же последовательности
на том же исходном образе и маршруте с единственным добавлением вызова
`_ensure_player_cache()` завершил первый трек, а второй и третий получили
естественный HTTP `403` при первом обращении к аудио-CDN. Отказ не внедрялся
тестом. Токены между записями отличались.

| Вариант | Полные записи | Отказ |
| --- | ---: | --- |
| Штатный обработчик yt-dlp, исходный маршрут | 3/3 | Нет |
| Тот же образ и маршрут, включён кэш предобработки Soundspan | 1/3 | CDN 403 на следующих двух записях |
| Исправленный образ, обычный клиент + MWEB/PO | 6/6 | Нет |
| Повтор после выпуска, свежий процесс с production-образом и его сетью | 6/6 | Нет |

verify: отдельные эксперименты с закреплённым IPv4 в Германии и другим
исходящим IP в Финляндии не устранили повторный отказ при включённом кэше.
Маршрут не признан причиной воспроизведённой ошибки. Временные прокси удалены.

Кэш сериализованной EJS-предобработки исключён. Совместимый startup-hook
возвращает `False` и сохраняет реестр штатных обработчиков yt-dlp. Положительный
ответ JavaScript-обработчика не используется как доказательство пригодности
ссылки для CDN. Медиа-spool, контекст анонимного посетителя, ограничения
параллельности, паузы запросов и ограниченное восстановление потока сохранены.
Контракт описан в [документации обработки YouTube](../YOUTUBE_PLAYER_CACHE.md).

## Приёмка

verify: регрессионный тест сначала дал два ожидаемых падения на исходном
коде, затем прошёл последовательную и параллельную регистрацию. YouTube suite:
650 passed, 4 skipped; целевые проверки регистрации, PO, отмены и продолжения
потока: 25 passed. Ruff, форматирование и строгий mypy изменённого Python-кода
прошли. Образ собран из точного предыдущего production-образа без обновления
зависимостей.

verify: в canary и при повторе после выпуска все шесть полных загрузок
декодированы FFmpeg; для каждой записи обычный клиент и MWEB/PO дали одинаковые
байты и SHA-256. Все шесть отложенных запросов последних 4096 байт дали `206`.
Свежие проверки обходили дисковый media-spool, чтобы он не скрывал ошибку
получения ссылки. Это отдельный процесс в сети production, а не подмена
настроек обслуживающего пользователей процесса.

verify: через публичный HTTPS API пройдены полный файл, две побайтно сверенные
Range-выборки и повторный вход для каждой записи:

verify: проверены обновление сессии, запрет административного API обычному
пользователю и поиск (2,24 с). Публичный путь может использовать готовый spool;
доказательством исправления извлечения служит отдельная последовательность

verify: readiness публичного сайта — `200`; после выпуска на контрольном
интервале 12 сентября 23:52:36 — 13 сентября 00:01:51 UTC в проверенных логах
YouTube, API, worker и frontend отсутствовали CAPTCHA, CDN 403 и ошибки потока.
У этих компонентов не было перезапусков и OOM. PO-компаньон использует прежний
logging driver `none`: его логи недоступны, работоспособность проверена
получением токенов и полным аудио, а не отсутствием записей в логе.

## Adversarial review и границы результата

verify: обычное ревью дополнено adversarial-review по регистрации, повторным
и параллельным запросам, отмене, восстановлению потока, секретам и откату.
Вердикт CLEAN; подтверждённых P0/P1/P2 в этой коррекции нет.

- Исправлена воспроизведённая локальная причина нерабочих ссылок, в том числе
  в пути PO-восстановления. Полное и постоянное отсутствие внешней CAPTCHA
  Google не доказано. Этот результат не объясняет автоматически все прежние
  отказы клиента VISIONOS или остановки на телефоне.
- Убрана оптимизация JS-зависимого пути; обработка может занимать больше CPU
  и времени. Обычный HIGH-shortcut VISIONOS не требует этой предобработки.
- Проверены три записи, а не весь каталог. Длительное воспроизведение на
  физическом телефоне с блокировкой экрана и сменой сети не проверялось.
- Полный Python mypy-gate с прежними 210 ошибками в 19 тестовых файлах не
  исправлялся этим выпуском. Отдельная проверка изменённого кода прошла.
