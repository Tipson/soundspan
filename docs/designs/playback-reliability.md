# Надёжность воспроизведения и внешних метаданных

Status: design phase (implementation verified locally; production acceptance pending)

## Продолжение аудио после отказа CDN

Один загрузчик владеет временным файлом, лимитом диска и потоком конкретной записи.
При `401`, `403` или `410` после первых переданных байтов он один раз удаляет
отклонённую ссылку из кеша и получает свежую через существующую очередь извлечения.
Повторная загрузка проверяет размер представления и SHA-256 всего уже переданного
префикса. Только совпавшее продолжение дописывается в файл; префикс повторно
пользователю не отправляется. Другой контейнер, изменившиеся байты, повторный отказ
или отмена запроса завершают восстановление. Общий срок загрузки не продлевается.

Нативный плеер сохраняет бюджет трёх автоматических попыток в пределах загрузки
источника. Событие `playing` может возникнуть на коротком буферизованном фрагменте
и не обнуляет этот бюджет. Явная новая загрузка или ручной повтор дают новую попытку.
После окончательного отказа применяется существующее восстановление через точную
запись серверного источника; очередь и идентичность композиции сохраняются.

Данные композиции запрашиваются из публичного каталога. Личная YouTube-сессия не
участвует в этом запросе. Отказ авторизации публичного поставщика возвращается как
ошибка upstream `502`, а не как утрата сессии Soundspan.

## Метаданные и ограничение нагрузки

Быстрый поиск Last.fm получает поля ответа поиска без дополнительных запросов за
биографией и обложкой каждого результата. Дедлайн передаётся в очередь и HTTP-клиент;
отменённая задача удаляется из очереди, а ожидание повторной попытки прерывается.
Неудачный быстрый поиск не становится успешным пустым ответом в общем кеше Discovery.

Все HTTP-запросы MusicBrainz, включая последовательные запасные варианты поиска,
получают общий слот Redis `soundspan:musicbrainz:dispatch:v1` на 1600 мс. Из них
500 мс отведены на доставку ответа Redis; запоздавшее разрешение не используется.
Это сохраняет не менее 1100 мс между отправками даже при задержке ответа координатора.
API и worker используют один ключ. Ожидание слота ограничено 2500 мс; проверка Redis —
500 мс. При недоступности координации используется имеющийся кеш или результат
отложенного необязательного обогащения, без неконтролируемых внешних запросов.
Ответы `429` и `503` устанавливают общую паузу 30–60 секунд. Повторные обращения во
время паузы не продлевают её. Неудачный поиск альбома или записи кешируется на
120 секунд; подтверждённое отсутствие результата — на один час.

MusicBrainz ограничивает запросы по общему исходящему IP. Другие приложения с тем
же адресом также расходуют этот лимит; координация Soundspan распространяется на
его собственные процессы. См. [правила MusicBrainz](https://musicbrainz.org/doc/MusicBrainz_API/Rate_Limiting).

## Конкурентные отметки показов

Транзакция обновления показов сначала блокирует принадлежащую пользователю выдачу
`RecommendationGeneration` через `FOR NO KEY UPDATE`. Затем Prisma отмечает только
ещё не просмотренные записи этой выдачи. Перекрывающиеся пачки не захватывают строки
показов в разных порядках; повторная отправка не перезаписывает исходное время.
Проверка владельца и признака `served` сохраняется внутри транзакции. Схема БД и
история существующих пользователей не изменяются.

## Граница проверки

Регрессионные тесты покрывают отказ после публикации префикса, его несовпадение,
отмену и исчерпание восстановления. Интеграционные проверки используют отдельные
PostgreSQL и Redis с одноразовыми данными. Полный HTTP-ответ, декодирование аудио,
работа браузера и физического телефона являются отдельными уровнями приёмки.
Работа восстановления при внесённом отказе не доказывает постоянного отсутствия
CAPTCHA или других ограничений внешнего поставщика.
