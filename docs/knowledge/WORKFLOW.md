# Совместная работа и обновление контекста

## Перед задачей

1. Проверить `git status`, remote, текущую ветку и открытые [PR](https://github.com/Tipson/soundspan/pulls) и [issues](https://github.com/Tipson/soundspan/issues).
2. Выполнить `git fetch origin`; посмотреть изменения общей базы относительно `origin/dev`. Не делать reset, checkout поверх локальных правок или force push для получения свежей документации.
3. Прочитать [STATE](STATE.md), [DECISIONS](DECISIONS.md), [ROADMAP](ROADMAP.md) и README нужной области.
4. Зафиксировать согласованную задачу: цель, ответственный, ветка, область файлов и критерии проверки. Использовать описание задачи или PR, а не копировать статусы GitHub во вторую ручную доску.
5. Если другой участник меняет те же файлы, договориться о границе до редактирования. Прочитанный бэклог не резервирует задачу и не возобновляет весь приостановленный цикл.

## Ветка и приёмка

Работа ведётся в `codex/<участник>-<задача>`. PR задачи направляется в `dev`; владелец объединяет принятый пакет через PR `dev` → `main`. Конкретные push и публикация выполняются в пределах поручения пользователя. Не считать write-доступ отдельным разрешением выпускать сайт или менять production data.

Изменения кода и связанного контекста проходят в одном PR. Предпочитать небольшие смысловые правки. Перед правкой общего STATE посмотреть последний diff, чтобы не затереть свежую запись другого участника целым старым файлом. Конфликты разбирать по фактическим результатам; не выбирать одну сторону целиком ради зелёного merge.

Если задача уже опубликована в общей ветке, интегрировать свежую `origin/dev` обычным merge при необходимости. Rebase, требующий force push в опубликованную ветку, без отдельного разрешения не использовать.

## Что обновлять

| Изменение                                                   | Документ                                                               |
| ----------------------------------------------------------- | ---------------------------------------------------------------------- |
| Поведение, внедрение, проверенная или непроверенная область | [STATE](STATE.md)                                                      |
| Принятое продуктовое или архитектурное решение              | [DECISIONS](DECISIONS.md)                                              |
| Владелец модуля, поток данных или граница                   | [Карта кода](ARCHITECTURE.md) и профильный README                      |
| Задача принята, частична, отложена, на паузе                | [ROADMAP](ROADMAP.md) и соответствующий issue/PR                       |
| Настройка окружения или способ работы                       | [DEVELOPMENT](DEVELOPMENT.md), [CONTRIBUTING](../../CONTRIBUTING.md)   |
| Датированная проверка релиза или устройства                 | [Release notes](../release-notes/) с точным source/ref и ограничениями |

Использовать [шаблон обновления](templates/change.md). Если задача не меняет ни одного из этих фактов, не добавлять формальную запись ради счётчика. Не помещать в продуктовый интерфейс внутренние статусы генерации, release bookkeeping и диагностические объяснения, если они не помогают пользователю выполнить действие.

## Проверки и доказательства

Сначала выполняются относящиеся к изменению тесты. Полный gate применяется к зафиксированному пакету по [AGENTS](../../AGENTS.md) и повторяется при новых изменениях или нерешённой причине отказа. Для чистой документации нужны проверка содержания, ссылок, форматирования и отсутствия приватных данных; она не означает новую сборку или приёмку приложения.

Проверять actual CI, а не только общий цвет PR. Quality Visibility автоматически охватывает PR в `main`, но не в `dev`. Поэтому наличие зелёных проверок у `dev` PR не даёт права заявлять полный backend coverage. Менять triggers или required checks можно только отдельной задачей; этот процесс не является таким изменением.

Build/test, реальный HTTP, браузер, production и физическое устройство — разные доказательства. Для внешних side effects, schema/data, ownership, storage, retries, concurrency и source integrations применяется отдельный adversarial-проход согласно правилам проекта. Историческое измерение переносится с границей source/runtime, а не как свежий PASS.

## Как фиксировать выпуск

Merge в `main` — состояние исходников. Сайт и APK объявляются обновлёнными только после выполнения выпуска и независимых postconditions. Подтверждённый выпуск получает отдельную release note и ссылку из STATE. Правка только контекста после выпуска не требует повторного развёртывания того же runtime.

## Приватное и предложения

Универсальная инструкция не содержит production credentials, подписанных media URLs, cookie/session dumps, private host profiles, персональных логов пользователей и ключа APK. Для воспроизведения использовать свои данные; редактировать только разрешённый scope.

Защита веток, обязательные review и расширение CI на `dev` остаются предложениями до отдельного подтверждённого изменения GitHub. Соглашение о PR не подменяет техническое ограничение прав. Личный Obsidian сохраняет приватные операции и архив; общей текущей сводкой служит эта папка.
